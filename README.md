# SQL Analytics Dashboard

[![CI](https://github.com/Purvee25/sql-analytics-dashboard/actions/workflows/ci.yml/badge.svg)](https://github.com/Purvee25/sql-analytics-dashboard/actions)
[![Python 3.11+](https://img.shields.io/badge/python-3.11+-blue.svg)](https://www.python.org/)

An end-to-end business analytics dashboard over a synthetic Indian e-commerce dataset.
Five business questions answered entirely in **named SQL files**, executed by **DuckDB**,
visualised with **Plotly**, and served via **Streamlit**.

**[▶ Live demo](https://purvee25-sql-analytics-dashboard.streamlit.app)** *(deploy instructions below)*

---

## Business questions answered

| # | Question | SQL file |
|---|---|---|
| 1 | How is monthly revenue trending, and what is the MoM growth rate? | `queries/01_revenue_trends.sql` |
| 2 | Which customers are Champions, Loyal, At-Risk, or Lost? (RFM) | `queries/02_customer_segments.sql` |
| 3 | Which product categories drive the most revenue and margin — and which have the highest return rate? | `queries/03_product_performance.sql` |
| 4 | What % of each monthly cohort returns in months 1–6? | `queries/04_cohort_retention.sql` |
| 5 | Which seller tiers hit their promised delivery SLA? | `queries/05_seller_sla.sql` |

## Architecture

```
data/generate.py
   │  Faker + Python → 5 CSV files (2 k customers, 300 products,
   │  80 sellers, 12 k orders, ~30 k line items)
   │  Growth trend, thin-file noise, and late-delivery patterns baked in.
   ▼
data/*.csv  ◄── never committed (gitignored); regenerate in ~5 s
   │
   ▼
dashboard/query_runner.py
   │  Reads queries/<name>.sql
   │  Substitutes CSV file paths via {table_name} placeholders
   │  Executes in an in-memory DuckDB connection
   │  Returns a pandas DataFrame
   │
   ├──► dashboard/charts.py   Plotly figure builders (one function per chart)
   │
   └──► dashboard/app.py      Streamlit: 5 tabs, KPI metrics, SQL expanders,
                              raw-data expander, sidebar nav
```

**Why DuckDB, not SQLite or pandas?**
DuckDB runs ANSI SQL (window functions, `DATE_TRUNC`, `NTILE`, `LAG`) directly on
CSV files — no import step, no schema migration, no server. It's the standard tool
for analytical SQL on local files, and it's what modern data teams use before
graduating to BigQuery/Redshift.

## Dataset

Synthetic Indian e-commerce, generated by `data/generate.py` (reproducible — fixed seed).

| Table | Rows | Key columns |
|---|---|---|
| `customers` | 2,000 | customer_id, city, state, signup_date, segment |
| `products` | 300 | product_id, category, cost_price, selling_price |
| `sellers` | 80 | seller_id, tier (1/2/3), city |
| `orders` | 12,000 | order_id, customer_id, seller_id, order_date, promised_delivery, actual_delivery, status |
| `order_items` | ~30,000 | order_id, product_id, quantity, unit_price |

Design choices worth noting in interviews:
- **Tier-1 sellers** are faster and more reliable than tier-3; lateness probabilities are baked in.
- **Order volume** skews toward later months (growth story for cohort analysis to pick up).
- **8 product categories** have realistic cost/margin profiles and different return-rate behaviours.

## SQL highlights

**Window function — MoM growth** (`01_revenue_trends.sql`):
```sql
ROUND(
    (revenue - LAG(revenue) OVER (ORDER BY month))
    / NULLIF(LAG(revenue) OVER (ORDER BY month), 0) * 100,
    1
) AS mom_growth_pct
```

**RFM segmentation with NTILE** (`02_customer_segments.sql`):
```sql
NTILE(4) OVER (ORDER BY recency_days ASC)  AS r_score,
NTILE(4) OVER (ORDER BY frequency    DESC) AS f_score,
NTILE(4) OVER (ORDER BY monetary     DESC) AS m_score
```

**Cohort retention** (`04_cohort_retention.sql`):
```sql
DATE_DIFF('month', f.cohort_month, cm.order_month) AS month_number
```

## Deploy to Streamlit Cloud (free)

1. Push to GitHub (CSV files are gitignored — `generate.py` runs on startup automatically).
2. Go to [share.streamlit.io](https://share.streamlit.io) → New app.
3. Set **Main file path** to `dashboard/app.py`.
4. Deploy. The app calls `generate.py` on first load if CSVs are missing.

## Known limitations

- **Synthetic data** — magnitudes are illustrative, not real market figures.
- **In-memory DuckDB** — a fresh connection per query; fine at this scale, but a persistent file-backed DB would be faster for larger datasets.
- **No auth / multi-user state** — Streamlit's `st.cache_data` is process-local; a shared deployment would need a backend store.
